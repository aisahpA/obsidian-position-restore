# 待议清单（review notes）

读代码时冒出来的疑问、想改的地方，**一律先落到这里**。为什么这样做见 `AGENTS.md` §2 第 8 条 ——
简言之：边读边改会把中文化的批次差分搅浑，憋到最后又会忘掉大半。

## 每条一段，四个字段

- **在哪**：`文件:行`（能指到函数就更好）
- **现状**：现在是怎么写的
- **疑问 / 建议**：觉得哪里不对、想要什么效果
- **状态**：`待议` / `已改`（写下 commit）/ `不改`（**必须写理由**）

「不改」这一类最值钱：连同理由留档，同一个想法将来不会被第八次重新提出来处理一遍。

## 处理顺序怎么排（详见 `AGENTS.md` §2）

改前先问它是哪一类，别一刀切：

| 想改的东西 | 怎么办 |
|---|---|
| 已译文件的注释措辞 / 说错的 WHY | 现在就改，注释-only 提交 |
| 单点 bug（任何文件） | 现在就修 —— 翻译只换语言，不会把 bug 修好 |
| 跨模块重构 / 改公共词汇（`placeKey`、`landing` 判据、"什么算一步"这类） | 等中文化全部跑完再动，否则已译批次要整批重译 |
| 还没译的文件 | 先改后译更省：译的时候直接按新代码写 |

一条例外比上面都重要：**凡是看起来"冗余、顺手就能修好"的地方，先翻 `MEMORY-detail.md` 对应的那一节**。
注释里大量句子是在挡后来者（「别加某某判断」「不许改成事件驱动」「不要加 memo 优化」），
它们看着像废话，实际是踩过坑的留痕。`AGENTS.md` §7 那份「已经撤销过、不许再捡回来」的清单就是这类。

- **现状**（2026-10-02 实测）：独立注释 **4332** 行 + 行尾注释 **205** 行 ≈ 4537 行，折成

## 附：怎么一眼看出谁在用、谁在改

不用文档（会过期），也不用改代码 —— 三条命令随时可重跑：

```bash
# 谁读了哪个键（次数从高到低）
rg -o --no-filename 'settings\.\w+' src/ | sort | uniq -c | sort -rn

# 谁在按名字写（现应只剩两处；注意 [^=] 是为了不把 === 比较算进来）
rg -n 'settings\.\w+\s*=[^=]' src/

# 谁接收了 settings（构造注入的全部签名）
rg -n 'settings:\s*(Partial<)?PluginSettings' src/
```

⚠️ 但**最重要的那个写点 grep 抓不到**：唯一正规写入口 `settings/tab.ts:56` 用的是动态键
（`(this.plugin.settings as ...)[key] = value`），任何按名字的查询都永远看不见它。这正是
「谁在改」不该靠 grep、而该靠**设计**（写入口收敛到一处 + 注释里标明它是唯一入口）的理由 ——
现状给的正是这个设计。
