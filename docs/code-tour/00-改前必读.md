# 00 改前必读：动手之前先看这里

`01`~`06` 讲**这段代码在干什么**；这一篇讲**动了会坏什么**。两者是不同的问题：
读懂了代码不代表知道它的约束从哪来。

- 只读代码、想弄明白机制 → 读 `01`~`06`，按目录顺序。
- **准备动手改** → 先在这一篇里查你要动的模块，然后去看它指的那一节。
- 想知道「当初为什么这么定」 → 顺着每条规则后面的 `→ detail「节名」` 去 AI 记忆
  （`MEMORY-detail.md`，真身在 Obsidian vault，**不进 git**）；引号里就是那边的章节标题。
  ⚠️ **读不到那边的东西不影响动手**：那边只装 WHY 与实测，这一篇里的判据是完整自洽的。

**每一条规则后面都带可 cmd+click 的源码链接**（形如 `` [`符号名`](/src/foo.ts#L120) ``）——
行号会随代码漂移，§9 有一条命令批量复查，唯一定义的符号还能 `--fix` 自动刷新。

## 1. 十二条最常踩的

按「踩了会静默坏掉」排序，不按模块排。

1. **阅读模式没有「可显示的光标」，但 `editor` 一直在。**
   `MarkdownView.editor` 恒存在（`setMode` 只搬 `scroll` + `fold`，**从不碰 selection**）⇒
   阅读模式 `setCursor` 是有效的。别把这话读成「阅读模式不能有光标」：
   [`flashLine()`](/src/position/ui/cue.ts#L110) 里那句「阅读视图压根没有行元素可说」谈的是**渲染出来的行
   元素**，不是 `editor` 对象 —— **照它写的 `getMode()` 守卫是错的**。→ detail「到页顶 / 到页底」

2. **切模式 / resize 会把落点打回**（`2be6916`，手机 + 电脑都复现）。
   根因在 app：`setMode(e){ i=this.scroll; … e.setEphemeralState({scroll:i}) }` 携带的是
   **own 字段 `view.scroll`** 而非 DOM；填它的是 `syncScroll()`，而**阅读模式的 `onScroll` 有
   100ms 渲染门** ⇒ 我们直接写 `scrollTop` 永远进不去。
   **修法只有一条路**：`syncViewScroll(view)` 在 `holdEdge` 之后（bracket 内）调
   `view.setEphemeralState({scroll})` —— 与 `setMode` 同一扇门。
   ⚠️ 别对阅读模式做「读 DOM 再写回去」。→ detail「到页顶 / 到页底 · 切模式」

3. **编辑模式下别去 `scrollIntoView` 光标** —— core 自己在 `setState` 时还原原滚动，你那样做会打架。

4. **`leaf.id` 跨会话稳定。** 布局序列化带着 id，重启后恢复出来的每个标签页还是原来那个 id。
   ⇒ 持久化的 `entry.leafId` 重启后仍指得着那个标签页。
   ⚠️ **别加「重启后按 path 找 leaf」的兜底** —— 会盖掉「回到它当时所在的那个标签页」这条刻意语义。→ detail「视图条目」

5. **`FileView` 没有 `file` 不算目的地**，否则删文件那一瞬会铸出 `view:markdown` 幽灵行。
   ⚠️ 别用「什么不是地点」那道黑名单（[`NON_DESTINATION_VIEW_TYPES`](/src/nav/entry.ts#L82)）堵
   —— 那道门与栈共用。→ detail「视图条目」

6. **这份列表只装笔记，不装位置**（2026-10-05 起）。一次 `jump`（大纲点击 / 标题链接 /
   搜索命中）在 `remember` 里**一律降级成 `visit`**（[`remember()`](/src/recent-files/places.ts#L294)），
   所以**一条记录 = 一行**，身份就是它的 path（无路径视图是它的视图类型，`navGroupKey`），
   **没有第二套身份**（`placeKey` 已删）、**没有第二个池子**。
   ⇒ **一落点 = 一记录 / `absorbSameLanding` / `forgetLanding` / `landingKeys` 都随它一起走了。**
   落点没有丢：它在**前进/后退栈**里（`NavStack` 照记 jump、且带 `st`）。→ detail「方案 0」

7. **搜索 / 块引用命中的跳转不进最近文件**（降级成 visit），**但后退栈照记**。
   规则只写在 `NavPlaces` —— funnel / stack / patcher **不动**。判据共享在 `src/nav/entry.ts`
   （[`isCallerKey`](/src/nav/entry.ts#L124) / [`isBlockKey`](/src/nav/entry.ts#L161) / [`blockAnchor`](/src/nav/entry.ts#L145) / [`stripLinkAlias`](/src/nav/entry.ts#L132)），
   别再手写 `startsWith('caller:')`。→ detail「带键跳转的链接文本」、「方案 0」

8. **`prop[: value]` 只认自有属性**（`hasOwnProperty`）。用 `in` 会让 `toString` / `constructor`
   命中每一篇笔记。⚠️ 别用 `Object.hasOwn`（tsconfig 的 lib 是 es2021）。
   **属性名区分大小写**；选择器要取 `getAllPropertyInfos()` 的 **`values().name`** ——
   那个 `key` 是小写折叠过的，取 `key` 永不命中。

9. **「别名」只指 `aliases`。** `title` 是笔记自称，不是别名。两者都走 `reads.otherNamesFor`，
   搜索面两种都算。hover 分两行，引导词用属性名本身（`recentFiles.title` / `.aliases`），
   **小写**、中英文一致。→ detail「hover 上的名字」

10. **重画成本几乎全是 DOM**（随行数线性增长）⇒ 只做「少画几次」「别全量重建」。
    **memo / 脏标记 / 合并重画都别做**，得不偿失。→ detail「面板重画」

11. **落地行为变了 ⇒ 改使用层，别顺手改采集层。**
    这是 09-28 踩出来的元规则（用户一度说「落点记录只要行号、不要光标」，试过让
    `readLandingState` 不写 cursor，**纯属多余、已撤**）：`landedLine` = `keyLine ?? st.scroll ?? cursor.from.line`，
    只要 `st` 不空就答得出来 ⇒ **每条 jump 的光标都被使用层重算**，采集层写没写 cursor 根本不影响结果。
    撤掉那笔后 887 个用例全绿。**多写一笔采集只会让两处知识重叠。** → detail「跳到标题」

12. **`armLandingMark` 只有一个 arm 点** —— `execute()` 开头。
    跨 pane / 跨 tab / 原生 delegate / 同文件 apply，**每个分支落到的都是这一条自带的位置**；
    放在某一个分支里就会漏掉另外几个（第一版放在两处，仍漏了「跨 tab 重新激活原叶」那条经 `openInLeaf` 的路）。
    jump/visit/teleport 三种步都武装（`view` 除外），编辑模式下**都居中、落定后都闪**；
    visit/teleport 带 `sourceOnly`，阅读模式不闪。同理 `pendingLineFlash` 带 `at` **到期作废**。
    ⚠️ 它同时是**面包屑该念哪一节**的那个锚（[`markLandingLine()`](/src/position/restore/modes.ts#L506)
    的返回值 → [`show()`](/src/position/ui/cue.ts#L78) 的第二个参数）：一次点名了一行的跳转
    把落点摆在视口**正中**，视口顶落在它**上方半屏**处 —— 拿视口顶命名就会念出上一个小节的名字
    （2026-10-09 用户报的「误报……上面顶部的章节」）。只有普通的保存位置恢复给不出落点行
    （那次落点**就是**视口顶）。→ detail「跳到标题」

## 2. 动 `src/position/restore/` 之前

- **光标要两个模式都放**。阅读模式放完切回编辑，光标就在那儿（见 §1.1 / §1.2）。
- **`holdEdge` 必须在 `syncViewScroll` 之前完成**（bracket 内的顺序是硬的）。
- **`src/position/restore/pixels.ts` 的三段结构**：先 `settleSourcePixels`（**masked 路径**：遮罩揭开**前**）→ 再 `relandSourcePixels`
  （揭开**后**的一次性检查）→ 然后**第二阶段**收敛验证。**最多 2 次纠正**，超了就不动。
  与它们并列的还有两个「盖布下跑」的：**只等不纠正**的 [`settleShortCover`](/src/position/restore/pixels.ts#L346)
  （源码注入 open 的可见短盖，见下面那条）与后台标签页的 `settleAndHold`。
  `HOLD_MAX_MS` = 400ms、`HOLD_CORRECTIONS` = 2（[`edges.ts:17`](/src/position/edges.ts#L17)），
  监听 `pointerdown/touchstart/wheel/keydown`（capture + once）；`el.isConnected` 为假即停。→ detail「到页顶 / 到页底」、「面板重画」
- **读 scroll 有三级，别混用**：①回读 / 校验 / 重落 + poll ⇒ 实时 `getScroll()`；
  ②导航 `readNavEntryState` ⇒ DOM 不在 layout 时才用 `view.scroll`（own 字段，须 cast）；
  ③desktop 的 `onScrollCapture` ⇒ `readSampledState`。
  **移动端 scroll 事件会丢 ⇒ 任何路径都不许用缓存值。**
- `st.scroll` 是**视口顶那一行的行号**（0 起算），**不是像素**。「当时 → 现在」的重锚
  只剩栈与恢复这一条路：[`resolveAnchorLine`](/src/position/restore/anchor.ts#L42)
  只在前进 / 后退 / 跳转的那次 apply 上跑（标题 / 块 id 结构化锚点，解不出由调用方退回
  文本片段 remap）。最近文件列表**不做任何换算**，行号直接取位置数据库（见本文 §5
  「一行的行号只有一处来源」）—— 旧的 mtime 闸门 → live editor → 磁盘文本三级链
  已随 `now-line.ts` 于 2026-10-05 撤掉，别加回来。
  ⚠️ **`getScroll()` 不是整数**：它给 0-based 顶行行号**外加该行已被滚过的比例**（`42.37`
  = 顶端落在第 43 行的 37% 处）⇒ 量化到整行是 `Math.round(getScroll())`，**不是** `+0.5`。
  理由见 [`ephemeral.ts:25`](/src/position/capture/ephemeral.ts#L25)：存小数会逼眼睛重扫断行，高块（图片/嵌入）会恢复出半张图。
  ⚠️ 还有个坑：预览渲染器没跟上时它报的是 **`null` 而不是 `undefined`** ——
  `isNaN(null)` 是 false（会绕过旧守卫）、`Math.round(null)` 是 0（会被读成「文件顶部」），
  所以必须用 `scroll == null || !Number.isFinite(scroll)` 挡。
- **阅读恢复的遮罩要盖到「真落定」，而且整段只用一条预算**：预览渲染器**分趟**跑（每趟 5ms，
  下一趟排在 rAF 上），且它的 `applyScroll` 第一句就是「目标行**之前**的每个 section 都必须
  已渲染并量过高度，否则拒绝」⇒ **什么时候能落由渲染器决定，与谁先请求、什么时候请求都无关**。
  拿源码那份 600ms（[`RESTORE_PAINT_DEADLINE`](/src/shared/wait.ts#L23)）去盖阅读，稍微大一点的
  笔记就盖不住：遮罩提前揭开，读者先看见还在顶部的半成品，而那次没能落下去、被排进渲染器
  `rendered` 队列的施加随后才生效 —— 就是「先看见顶部、再接着跳」。
  ⚠️ **「内容就绪」与「揭幕确认」必须共享同一条 deadline**
  （[`RESTORE_MASK_BUDGET_PREVIEW`](/src/shared/wait.ts#L40)）：拆成两条独立预算会**相加**，
  曾经就是 2000 + 2000 = 4 秒。读者能感知的只有「盖上到揭开」这一段，所以只该有一个数 ——
  1500 是用户真机上见过 4 秒之后拍的（2026-10-08）。
  ⚠️ 这个数**就是空白的代价**，别指望找到两边都占的招：渲染器必须从顶部一路渲染到目标行，
  这段时间读者要么看着内容逐段长出来（然后跳），要么看着遮罩（等）。它只能是「遮到什么时候放弃」。
  ⚠️ **别指望「让阅读 open 也注入落点」来解决它**：注入只是把请求提前，落不落仍由渲染器那道
  `computed` 门说了算 —— 早请求 ≠ 早落（这条推演被推翻过一次，见 detail「阅读恢复的揭幕」）。
  ⚠️ 揭幕等待期间**读者一动就收手**：判据是 `Math.max(lastTouchAt, lastUserInputAt)` 越过本次
  恢复入口取的基准（两个平台各有一套信号，同 sampler 的 `hasUserIntent`），别把读者从他们自己
  的滚动里拽回来。
- **源码的注入 open 要遮，但只遮到「编辑器量完」为止**（2026-10-08/09 用户拍板，多轮真机实测定的）：
  这条路上「空白 ↔ 内容自己动」只能选一个侧重 —— 在编辑器量完行高之前画出来的帧必定被随后的
  一次测量推动（core 的两段式落地，实测约 85~145ms），不遮就看得见那几下。所以遮罩
  （[`maybeCoverOpen`](/src/position/restore/patcher.ts#L374)）是**必须的**，可调的只有时长
  （[`settleShortCover`](/src/position/restore/pixels.ts#L346)）。判据是**两个读数**在同一个窗口里都
  **没离开过窗口起点**：① 保存那一行相对滚动容器顶的偏移、② **视口里最后一条可见行**的同一
  偏移（`bottomVisibleMeasurer`：拿滚动容器底边去问 CM 那一点是哪一行）—— **只看 ① 是量错了
  地方**：重落把**同一行**落在同一个偏移上，动的是它下面那些刚从估算换成真值的区块，换算到
  屏幕上就是整条带子往下挪。**下限从「第一次量到真几何」那一刻起算**（core 的重落跟着内容交换走）
  加上 [`SOURCE_COVER_FLOOR_MS`](/src/position/restore/pixels.ts#L72)（150）；**上界从「读者看得见
  这道遮罩」那一刻起算**（[`appliedAt`](/src/position/ui/cover.ts#L61)）——
  [`SOURCE_COVER_MAX_MS`](/src/position/restore/pixels.ts#L73)（1000，到点照揭）是一条「别把读者按住
  太久」的界限。**遮罩在 open 一开始就涂上，两端一致**（2026-10-09 第十二轮之后改判）；但「**读者
  看得见**这道遮罩」的时刻两处不同：桌面上涂上就看得见；手机端那一刻全屏的文件列表还盖着正文，要等
  新内容进视图（[`markVisible`](/src/position/ui/cover.ts#L178)）。两个起点仍然不同（差一次测量），别合并。
  ⚠️ **「读盘那段留给旧画面」已经作废（旧「甲」）**：旧写法特意让桌面/平板**等新内容到了才涂**，理由是
  「别把一段纯 I/O 等待伪装成加载」。可真机上它读起来是**上一篇闪一下** —— 同 leaf 换文件时 core 要
  **异步读盘**（文件越大越久），文件不在内容缓存里时那几百 ms 屏幕上就是上一篇，接着才白、才换新，与
  点击快慢无关（结构性，2026-10-09 用户报「打开 C 时看见上一篇的内容闪一下」，**慢慢点也一样**）。
  所以现在**两端都在 `setViewState` 那一刻就涂上**（[`cover()`](/src/position/ui/cover.ts#L93)，
  不再有 `holdPrevious` 参数）：手机上选择文件的过程（原生列表、插件侧面板、对话框）本来就**全屏**盖住
  正文；而桌面那一次读盘通常**远小于短盖自己的下限**（`SOURCE_COVER_FLOOR_MS` 150），拿它换「屏幕上
  绝不会出现别的笔记」是划算的。
  判据是**两层，从粗到细**（[`contentSwapGate`](/src/position/restore/patcher.ts#L412)）：①
  `pixels.noteArrived` —— 编辑器里的**文档对象**换掉了没有（挡住「core 还在异步读盘」那几百 ms）；
  ② 按**内容**认「现在装的是不是**这一次**要打开的那篇」—— ⚠️ 第一层有个真洞：它只会答一次
  「换了」，**任何一个别的笔记都满足它**，而 core 的 `loadFile` 读盘回来**不复核**（见 ⑬），快速连点
  A→B→C 时中间篇就会在第一个「换了」上把短盖骗开。这道闸门与跨文件派发编辑器原语前那道等待**共用同一
  段闭包**（见 §5）；武装那一刻屏幕上就是同一篇（重放）或压根没有视图时这道闸门**缺席**（交回
  `undefined`）—— 那几种情形没有「上一篇」要留。
  ⚠️ **但「读不到编辑器」不许并进那几种里**：
  `MarkdownView.editor` 是 getter，视图刚建 / 刚重建时确实是 `undefined`，而「屏幕上本来就没有上一篇」
  与「有上一篇、但这一刻读不到它的文档」是**相反**的两种情况 —— 早先共用同一个 `undefined` 出口，
  于是后者被当成前者、闸门直接打开（遮罩立刻盖上、整条流水线跑在上一篇的几何上，2026-10-09 晚手机上
  「还是一样的」就是它）。读不到编辑器时照样返回一份身份、退到 `view.data` 比对（**空串算没到**）。
  ⚠️ **别加回来这十三样**：① 遮罩下的对齐纠正循环 —— 旧版把它和 ② 的静默窗口叠加在一起，下限因此
  约 250ms，「每次打开都先给出一段空白」就是它俩；② 100ms 静默窗口（只有读者看不见的后台那条路
  需要）；③ 把下限挪回从 `file-open` 起算 —— 它可能晚到连 core 的重落都过去了，那时候本该立刻揭；
  ④ 把下限挪回从遮罩盖上起算 —— 同 leaf 换大文件时它早于真几何到手，core 的重落于是落在揭开之后；
  ⑤ **把「没离开起点」改回「与上一帧比」** —— 测量是小步推进的，每帧挪几个像素（都不到半行）会让
  逐帧比较一路判「没动」，窗口照走、32ms 后揭开，而内容还在挪（手机上大文件就是这么漏的）；
  ⑥ **把第二个读数改回整篇文档的测量高度 `scrollHeight`** —— 视口**下方**的区块换成真值、嵌入的
  图片与嵌入笔记加载完，都会改总高度却改不动读者眼前那条带子，于是遮罩被一路按到上界
  （2026-10-09 用户报「稍微大一点的文件空白明显更长」正是它）；
  ⑦ **把「文档对象换掉了没有」改回「doc 与 `view.data` 相符」** —— core 的 `loadFile` 是
  「先换 `view.file` → `await` 读盘 → 最后 `setData`」，而 `setData` 又先写 `data` 再换文档：
  两者**一起**换，「相符」在读盘之前与之后都成立，等于没判。2026-10-09 实测：拿它当闸门，整条
  恢复流水线（居中、短盖）在没换过来之前就开跑，跑到**上一篇**的几何上 —— 旧文档的几何是稳的，
  短盖当场判定「量完了」而揭幕，读者看到的正是原生那套自己动。真正的读数只有**文档对象本身**
  （`pixels.docIdentity` / `noteArrived`）；
  ⑧ **把起手那两帧删掉**（`settleShortCover` 开头 `requestMeasure()` + 跨两帧再观察）—— `noteArrived`
  在 `setData` 那一刻就为真，而 CM6 只在 `state.doc` 上**同步**换文档，视口重算与 DOM 重画排在它
  自己的测量趟里（rAF）：起手立刻读，读到的是**旧文档的像素**（它是稳的）⇒ 读数一动不动 ⇒ 窗口
  走完就揭幕，紧接着编辑器才把新画面推上来（2026-10-09 晚手机上「内容出现后自己动」的最后一个洞）。
  同一条改动还把静默窗口改成 `max(32ms, 2 × 最近帧间隔)`，让慢设备按真实节奏攒证据，**别改回定值**；
  ⑨ **把 `namedLineAsk` 的「编辑器认不认那个原语」并回「点名了哪一行」** —— 合在一起会把「还没就位」
  误读成「没有要点名的行」，`centerNamedLine` 静默放弃居中、落点退回按行数估的种子（用户报的「位置
  完全不确定、有时不在屏内」）。两者分开判，`centerNamedLine` 在中间有界地等 `CENTER_READY_MAX_FRAMES`
  帧（按**帧**计 —— 这个洞只在「内容已到、编辑器还差一步挂上」时出现，那一步是视图构造里同步发生的；
  按毫秒计会让慢设备白等，也会把「编辑器本来就不认这原语」的桩一起拖住）；
  ⑩ **让重入时的判据「先来的说了算」**（`cover()` 写成三目 `existing ? existing.ready : ready`，
  或干脆留住最先武装的那道）—— 两种重入要的是**相反**的一边，这也是为什么它既不是纯三目、也不是纯
  「新的顶掉旧的」：
  · core 会**重放** `setViewState`（未激活标签页的延迟重建、快速切换器再次选中当前文件），重放那一刻
    leaf 上那个视图握着的**就是**这次要打开的文件，`contentSwapGate` 找不出「上一篇」的身份、只能交回
    **缺席**（`undefined`）。让缺席的顶掉先武装的闸门，**恢复流水线**整条跑在**旧文档**的几何上 ——
    旧文档是稳的，短盖当场判定「量完了」而揭幕，读者正看见新内容自己画出来（2026-10-09 手机上报的
    「还是看见源码渲染的过程」就是它）。所以**缺席时保住已有的那道**。
  · 但**换了文件**的重入（快速连点 A→B→C）是另一回事：那几道闸门问的都是「**这一篇**的内容进编辑器
    了吗」，而**留住最先武装的那道**会让短盖等在 A 上 —— 中间篇被画出来的那一瞬它就揭幕了
    （2026-10-09 用户报的「打开 C 时看见 A 的内容闪一下」）。所以**定义了的判据要顶掉旧的**：最后
    一次武装的那道（对应最后点的那个文件）说了算。
  两条合起来就是 [`cover()`](/src/position/ui/cover.ts#L93) 里那句 `ready ?? existing?.ready` ——
  **定义了的替换旧的、缺席的留给旧的**。⚠️ 别改回三目：它把「缺席」与「有定义但先到」混成一种，
  换文件时新判据永远顶不掉旧的。⚠️ 也别因为「上界起点 `appliedAt` 是先来的说了算」就类推到判据 ——
  两个数是两回事。
  ⑪ **把「读盘那段留给旧画面」加回来**（`cover()` 又等闸门开了才涂 / 又长出个 `holdPrevious` 平台
  分支）—— 旧「甲」的理由是「别把一段纯 I/O 等待伪装成加载」，可真机上那一次读盘（文件不在内容缓存
  里时）读起来就是**上一篇闪一下**，与点击快慢无关（结构性，2026-10-09 用户报的「打开 C 时看见上一篇
  的内容闪一下」，**慢慢点也一样**）。遮罩必须在 `setViewState` 那一刻就涂上、两端一致；那次读盘通常
  远小于短盖自己的下限，用「屏幕上绝不会出现别的笔记」换它是划算的。
  但**别顺手把「读者看得见这道遮罩」的起点也提前**（[`markVisible`](/src/position/ui/cover.ts#L178)）：
  手机上涂上那一刻全屏列表还盖着正文，短盖的上界要是从它起算，读盘与列表收起动画就把短盖的预算白吃掉
  （读得越久吃得越多，到点照揭、编辑器却还没量完）。两件事分开：**涂上**两端一致（就是 open 一开始），
  **读者看得见**手机端要等新内容进视图。
  ⚠️ **没有「上一篇」可比时（全新 leaf / 同一篇的重放）那道闸门是缺席的，不是「恒真」** —— 两者在
  「读者看得见了吗」这件事上不是一回事：全新 leaf 那一刻视图还没建出来，`contentSwapGate` 只能交回
  一个恒真的判据，而照它算，起点就落在「涂上容器背景」那一刻（全屏列表还没收完）⇒ 读盘与列表收起
  动画白吃掉短盖的预算 ⇒ 到点、循环还没量稳就揭幕（2026-10-09 手机上报的「列表一收，新内容闪一下」）。
  所以：`contentSwapGate` 那时交回 **`undefined`**（别写 `() => true`）、`markVisible` 手机端在
  闸门缺席时改问 leaf 自己「这篇内容进视图了吗」（`contentShown`）；而 `cover()` 里保判据写
  `ready ?? existing?.ready`（**定义了的替换旧的、缺席的留给旧的** —— 缺席不许顶掉、换文件又必须
  顶掉，两种重入都要照顾，详见 ⑩）。
  ⑫ **拿「取样点 / 已渲染范围」去问「屏上有没有标题」**（`cue.show()` 的 `hasVisibleHeading`）——
  面包屑**念的前提是屏幕上没有标题**（2026-10-09 用户拍板）：这一屏上有标题可看时，读者自己就知道
  在哪一节，复述是噪音。那道门的**判据换过三回、三次都取错了「哪一段」**：① `.cm-scroller` 上下有
  padding，贴着上下沿的取样点落进去 `posAtCoords` 答 null（屏上明明有标题也判「看不见」）；
  ② `.cm-content`（`contentDOM`）是**整篇内容**那块，矩形高度 = **整篇文档的高度**，长笔记滚到中段时
  取样点大半落在屏外；③ CM6 的 `viewport` 是**已渲染**范围、比可视区**大一圈**（标题刚滚出屏、还在
  渲染缓冲里也算「看得见」）⇒ 静默太多，用户报「点了多篇笔记只有一篇显示面包屑，就像完全消失了」。
  ⇒ **正确判据是量「标题自己的 DOM 矩形」与滚动容器的可见矩形求交**（源码模式取标题行的 `.cm-line`
  元素、阅读模式扫 `h1~h6`），`viewport` **只当「已渲染」的收窄条件、不当判据**。**别再用取样点 /
  已渲染范围去答「看没看见」**。另一道门是 [`breadcrumbPath`](/src/position/ui/cue.ts#L38)
  （笔记要真有 ≥2 个标题、落点得真落在某条标题链里）。
  ⑬ **把 `noteArrived` 当成「这一次要打开的那篇到了」**（[`contentSwapGate`](/src/position/restore/patcher.ts#L412)
  去掉按内容认的第二层）—— `noteArrived` 只会答一次「文档对象**换了**」，而**任何一个别的笔记都满足
  它**。core 的 `FileView.loadFile` 只在自己入口比一次 `this.file === file`，`await onLoadFile(file)`
  之后**没有任何复核**（2026-10-09 解包 `obsidian.asar` 实测核实；同文件的 `onDelete` 里倒是有这种
  守卫），所以快速连点 A→B→C 时 A 与 B 的读盘都可能晚于 C 回来、把**中间那篇**画上去 —— 而短盖在
  第一个「换了」上就揭幕了，随后晚到的那一篇一闪（2026-10-09 用户报的「打开 C 时看见 A 的内容闪
  一下」）。第二层用 `vault.cachedRead(file)` 拿目标文件内容与 `view.data` 比，按**文档身份**记忆结果
  （同一次交换只换一次文档对象 ⇒ 整段等待里最多比几次，不必每帧做 O(内容长度) 的比对）。取不到文件、
  或桩环境不认 `cachedRead` 时这一层**缺席**，退回只有第一层。
  ⚠️ 落点的精确纠正仍然只有揭开后的一次性检查
  （[`relandSourcePixels`](/src/position/restore/pixels.ts#L633)：只修半个视口以上的离谱误差，
  半屏内的偏差不追 —— 追它就是过去那场看得见的拉锯）。
  历史：先整条删掉遮罩 ⇒ 空白消失，但那几帧的变动露在明面上 ⇒ 改回短盖形态；再实测 ⇒ 大文件仍动
  （① 判据只盯目标行、② 下限早于交换完成）⇒ 扩成两个读数、下限锚到真几何；手机再实测 ⇒ 大文件仍动
  （③ 逐帧比漏掉小步推进）⇒ 改成与窗口起点比；再实测 ⇒ 空白仍偏长（读盘被涂成空白 + 第二个读数拿
  整篇高度）⇒ 读数换成视口里最后一条可见行，并把盖布推迟到新内容到位（旧「甲」）；**再实测 ⇒ 那个
  「推迟」在真机上就是「上一篇闪一下」（慢点也一样）⇒ 撤销旧「甲」，两端都在 open 一开始就涂上**。
  后台标签页那条路另有一套，读者看不见它，所以可以盖到静默为止
  （[`settleInjectedReveal`](/src/position/restore/modes.ts#L166)）。

  `editor.scrollIntoView(..., true)`）。于是 ① **别去调它** —— 2026-10-07 用户试过 `-1` → `-2`，
  真机上没有任何可感差别：它只喂种子，而差一行本来就落在下游纠正器那 ±2 行的死区里；
  ② 它只在两种时候才真的是落点：**居中做不到**（视图还没建好 / 编辑器不认那个原语 ——
  [`historyJumpApply()`](/src/position/restore/modes.ts#L321) 会把种子补落上去），以及
  **居中之前那一帧**。所以别把它删成 0：那样第一帧会离得很远，还会掉出纠正器的死区、被它们拽回去。

  `applyScroll` 是拿那一行所在的**区块**（`cm.lineBlockAt`）插值出来的 ——
  `区块顶 + (块内行偏移 + 小数) × 区块高 ÷ 区块行数`。一篇笔记里行高一不齐（标题、嵌入的图片、
  折行），「区块高 ÷ 区块行数」就是个平均值，落点必然差一点。**这就是这条落点不能靠行号算的
  根因**，也是 core 自己的大纲点击根本不走 `applyScroll`、而走 `scrollIntoView(..., true)` 的原因。

  ⚠️ 那条带子按**几何**算（[`topFadeBandPx()`](/src/shared/jump-landing.ts#L104)）：**顶栏底边
  减滚动容器顶边**就是被盖住的那一段 —— 顶栏在流里时内容就从它下面开始（差 ≤ 0 ⇒ 没有带子、
  一行都不让），顶栏被提成流外浮层时内容从它底下滚过（差 = 安全区 + 顶栏高）；再加 12px 的
  渐隐余量、按行高向上取整。⚠️ 别改成「问平台是不是手机」：手机的浮动导航**是可关的**
  （`floatingNavigation`，出厂开；关掉后顶栏回到流里、带子随之消失），按平台一刀切会凭白多让。
  ⚠️ **`--safe-area-inset-top` / `--view-header-height` 读不得**：两者的值本身还是 `env()`/`var()`
  的引用，真机上 `parseFloat` 出来是 NaN（2026-10-07 的第一版正是这样，看上去和「没做」一样）。
  ⚠️ 行 0 例外：`applyEphemeralState` 不施加一个 0 的 scroll，所以「第一行就是标题」的笔记
  仍落在文件顶上。
  ⚠️ **这个偏移只在造步时施加一次**，别在 `landingOf`/`applyLanding` 上再减一次：core 记一条
  大纲点击时记的本来就是**落定之后**的视口，重落一遍等于把已经居中的再往上挪半个视口。
  ⚠️ 而源码模式下**连造步时的那一次也不落**：一次点名一行的跳转由
  [`centerNamedLine()`](/src/position/restore/modes.ts#L408) 独占落点
  （[`historyJumpApply()`](/src/position/restore/modes.ts#L321) 先只落光标 —— core 的 `setState`
  在带光标时会把滚动原样还回去，所以那一步不移动视口），视口于是**只动一次**而且动在像素上；
  种子只在居中做不到时才补落。回读居中结果要**等编辑器真正应用那次滚动**（`scrollIntoView`
  是一个 effect，排在编辑器的测量趟里）：回读早了，下游那些「按 `st.scroll` 对齐到顶」的纠正器
  会把刚落好的视口又拽回去 —— 见 [`settledScroll()`](/src/position/restore/modes.ts#L439)。
  ⚠️ **跨文件时，派发之前必须先等文档就位**（2026-10-09 用户拍板；那道等待就是
  [`waitContentArrived`](/src/position/restore/modes.ts#L127)，判据与遮罩共用同一段闭包）：
  `file-open` 是防抖发出的，而同一个 leaf 上的文档交换是异步的 —— 两者之间那几百 ms 里编辑器
  握着的还是**上一个文件**。此刻派发的 `scrollIntoView` 行号被夹进旧文档的范围、回读到的也是旧
  文档的滚动 ⇒ 这次居中完全作废，落点交给按行数估的种子（用户报的「位置完全不固定、有时不在
  屏内」）。**等不到就干脆不居中**（退回种子）：一次落在旧文档上的居中的滚动 effect 可能在交换
  之后才被应用，把视口甩到任意位置 —— 比不居中更糟。
  ⚠️ 判据是**文档对象换掉了没有**（`pixels.noteArrived`）—— **别**回到「`view.data` 是 core 在
  交换**之前**就设好的」那个说法：`setData` 先写 `data` 再换文档，两者一起换（见 §2 第 ⑦ 条）。
  同文件跳转（`historyJumpApply`）不受影响：文档本就在位，那条路**不经过**这道等待。
  ⚠️ **另一头的坑：编辑器晚一步才挂上那个原语时不许放弃居中**（2026-10-09 晚，丙）。「这一步点名了
  哪一行」（`namedLineTarget`，只看标记）与「编辑器此刻认不认那个原语」（`namedLineAsk`）必须**分开
  判** —— 合在一起会把「还没就位」误读成「没有要点名的行」，`centerNamedLine` 于是静默放弃居中、落点
  退回按行数估的种子（用户报的「位置完全不确定、有时不在屏内」）。`centerNamedLine` 在两者之间最多等
  `CENTER_READY_MAX_FRAMES`（3）帧，按**帧**计（这个洞只在「内容已到、编辑器还差一步挂上」时出现，
  那一步是视图构造里同步发生的；按毫秒计会让慢设备白等，也会把「编辑器本来就不认这原语」的桩拖住）。
  → detail「跳到标题」
- **一行 = 一篇笔记**（§1.6 已立）：反复访问合并成**同一行**（`places.ts remember` 的重盖章），
